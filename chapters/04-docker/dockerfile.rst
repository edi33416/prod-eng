.. _ch04_dockerfile:

Writing Dockerfiles
====================

.. note::

   Work in your BookShelf project (or a copy of ``support/bookshelf-ch4/``). All commands
   on this page run from the project root — the directory containing ``pyproject.toml``.

-----

From Lockfile to Image
-----------------------

A ``Dockerfile`` is a recipe: a sequence of instructions, each of which produces one
image layer. Docker executes it top to bottom with ``docker build``.

The image needs the exact dependency versions you test with. You already have the tool
for that from :ref:`ch01_deps` — generate a runtime lockfile (no dev extras) if your
project does not have one yet:

.. code-block:: bash

   $ pip-compile --strip-extras --output-file=requirements.lock pyproject.toml
   $ head -12 requirements.lock
   #
   # This file is autogenerated by pip-compile with Python 3.12
   # by the following command:
   #
   #    pip-compile --output-file=requirements.lock --strip-extras pyproject.toml
   #
   annotated-doc==0.0.5
       # via fastapi
   annotated-types==0.8.0
       # via pydantic
   anyio==4.15.1
       # via

The image installs from ``requirements.lock``, not from ``pyproject.toml``. ``pyproject``
says what the project *accepts* (``fastapi>=0.111``); the lockfile says what was *tested*
(``fastapi==0.162.0``). Production gets the tested set.

-----

Dockerfile Instructions
------------------------

.. list-table::
   :header-rows: 1
   :widths: 18 82

   * - Instruction
     - What it does
   * - ``FROM``
     - Base image to build on. Every Dockerfile starts with one.
   * - ``WORKDIR``
     - Set (and create) the working directory for later instructions and for the
       container at runtime.
   * - ``COPY``
     - Copy files from the **build context** (the directory you pass to
       ``docker build``) into the image.
   * - ``RUN``
     - Execute a command at *build* time and save the resulting filesystem as a layer.
   * - ``ENV``
     - Set an environment variable, both for later build steps and at runtime.
   * - ``EXPOSE``
     - Document which port the application listens on. It does *not* publish the
       port — ``docker run -p`` does that.
   * - ``CMD``
     - Default command when the container starts. Overridable on ``docker run``.
   * - ``ENTRYPOINT``
     - Fixed executable for the container; ``CMD`` then supplies default *arguments*
       to it. Useful for CLI-tool images; for a web service, ``CMD`` alone is enough.
   * - ``USER``
     - User (and group) that later ``RUN`` steps and the container process run as.

A First Dockerfile for BookShelf
---------------------------------

Create ``Dockerfile`` in the project root:

.. code-block:: dockerfile

   FROM python:3.12-slim

   WORKDIR /app

   COPY requirements.lock .
   RUN pip install --no-cache-dir -r requirements.lock

   COPY src/ ./src/
   ENV PYTHONPATH=/app/src

   EXPOSE 8000
   CMD ["uvicorn", "bookshelf.main:app", "--host", "0.0.0.0", "--port", "8000"]

Line by line:

- ``python:3.12-slim`` — Debian with Python 3.12 and nothing else. The ``slim`` variant
  drops compilers and headers; you will see why that matters in :ref:`ch04_multistage`.
- ``--no-cache-dir`` — pip's download cache is useless inside an image and would add
  tens of megabytes to the layer.
- ``PYTHONPATH=/app/src`` — makes the ``bookshelf`` package importable from the
  ``src/`` layout without ``pip install``-ing the project itself.
- ``--host 0.0.0.0`` — inside a container, ``127.0.0.1`` is the *container's* loopback
  interface. A server bound to it is unreachable from the host, even with ``-p``. Bind
  to all interfaces.
- ``CMD [...]`` in **exec form** (a JSON array) — uvicorn runs directly as PID 1 and
  receives ``SIGTERM`` on ``docker stop``. The *shell form* (``CMD uvicorn ...``) wraps
  it in ``/bin/sh -c``, and the shell does not forward signals to its child.

.. warning::

   ``--host 127.0.0.1`` (uvicorn's default) is the single most common reason for "the
   container is running but ``curl`` fails". The symptom is
   ``curl: (52) Empty reply from server`` or ``Connection reset by peer``: Docker's
   port proxy accepts the connection, but nothing in the container is listening on the
   interface it forwards to. If you see that, check the bind address first.

.. admonition:: Observation:

   These ten lines are both a **recipe** and a **bill of materials**. As a recipe, they
   tell Docker how to assemble the image, step by step. As a bill of materials, they
   record everything the service is made of: the operating system and Python version
   (``FROM``), every library at an exact version (``requirements.lock``), the
   application code (``COPY src/``), and how it is configured and started (``ENV``,
   ``EXPOSE``, ``CMD``). Before, that knowledge lived in a wiki page or in someone's
   head. Now it is a file in the repository, reviewed and versioned with the code.

   The bill is only as precise as its pins. ``python:3.12-slim`` is a moving tag, and
   the Debian packages inside the base image are not listed here at all.
   :ref:`ch04_multistage` tightens the first point. For the second, scanners such as
   Trivy (Chapter 10) inspect the *built image* and can export a complete,
   machine-readable SBOM (Software Bill of Materials).

Building and Running
---------------------

The build command has two arguments worth understanding before you run it:

.. code-block:: text

   docker build -t bookshelf:v1 .
                   └───┬───┘└┬┘ └─ build context: the directory whose files COPY can see
                       │     └─── tag
                       └───────── repository (image name)

The trailing ``.`` is the **build context**, covered in the next section. ``-t`` (tag)
gives the image a name. Without it, the image is identified only by its content hash
(``sha256:4a681bc3…``), which is unique but not something you want to type.

Image names
^^^^^^^^^^^^

A full image reference has up to four parts:

.. code-block:: text

   [REGISTRY/][NAMESPACE/]REPOSITORY[:TAG]

   bookshelf:v1                          → docker.io/library/bookshelf:v1
   python:3.12-slim                      → docker.io/library/python:3.12-slim
   aquasec/trivy:0.57.0                  → docker.io/aquasec/trivy:0.57.0
   harbor.example.com/shop/bookshelf:v1  → a private registry (Chapter 10)

- **REGISTRY** is the server the image is pushed to and pulled from. It defaults to
  Docker Hub (``docker.io``).
- **NAMESPACE** is a user or organization on that registry. Official images like
  ``python`` live in the special ``library`` namespace.
- **REPOSITORY** is the image's name, here ``bookshelf``.
- **TAG** identifies a version within the repository. **It defaults to latest**, so
  ``docker build -t bookshelf .`` produces ``bookshelf:latest``.

Docker fills in the defaults silently. You can see it in the last line of the build
output below: ``naming to docker.io/library/bookshelf:v1``.

Tags are labels, not versions
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

A tag is a **movable pointer** to an image ID, like a Git branch pointing at a commit.
One image can carry several tags, either at build time (repeat ``-t``) or afterwards
with ``docker tag``:

.. code-block:: bash

   $ docker tag bookshelf:v1 bookshelf:latest
   $ docker build -q -t bookshelf:v1 -t bookshelf:0.3.0 .
   $ docker images bookshelf
   REPOSITORY   TAG       IMAGE ID       CREATED         SIZE
   bookshelf    0.3.0     4a681bc35317   2 minutes ago   195MB
   bookshelf    latest    4a681bc35317   2 minutes ago   195MB
   bookshelf    v1        4a681bc35317   2 minutes ago   195MB

Three tags, one image: same ID, and the 195 MB is stored once. Rebuilding with
``-t bookshelf:v1`` after a code change moves the ``v1`` label to the new image, and
the old image is left untagged (``<none>``). Two consequences for production:

- ``latest`` does **not** mean "newest". It is just the default tag name, pointing at
  whatever image was last tagged that way. Never deploy ``:latest``: you cannot tell
  what is running, and you cannot roll back to it.
- Tag releases with something meaningful and never reuse it: the application version
  (``0.3.0``, from ``pyproject.toml``) or the Git commit SHA. Chapter 5 tags every CI
  build with the commit SHA.

Two things should bother you. The API runs as **root**. And the SQLite database lives
**in the container's writable layer, next to the source code** — ``docker rm`` deletes
every book. Both are fixed later in this chapter.

The Build Context and .dockerignore File
-----------------------------------------

The ``.`` at the end of ``docker build`` is the **build context**: the set of files
the build is allowed to see. ``COPY`` paths are resolved relative to it, and nothing
outside it is reachable. ``COPY ../secrets .`` fails, by design.

The Docker daemon may run somewhere other than your shell (inside Docker Desktop's VM,
or on a remote host), so the context is transferred to it. BuildKit, the default
builder since Docker 23, only transfers the files that ``COPY`` instructions actually
reference. That is why the build above reported ``transferring context: 13.72kB``,
even though the project directory also holds a 126 MB ``.venv/`` and a ``.env``.

That protection disappears the moment a Dockerfile says ``COPY . .``, which is common
and convenient. Here is the same project with ``COPY . .`` instead of the two targeted
copies, and no ``.dockerignore``:

.. code-block:: bash

   $ docker build -f Dockerfile.copyall -t bookshelf:copyall .
    => [internal] load build context                                       1.5s
    => => transferring context: 108.35MB                                   1.5s
   ...
   $ docker images bookshelf:copyall
   REPOSITORY   TAG       IMAGE ID       CREATED          SIZE
   bookshelf    copyall   eb571512599a   3 seconds ago    302MB

   $ docker run --rm bookshelf:copyall ls -a /app
   .  ..  .env  .git  .gitignore  .venv  Dockerfile  Dockerfile.copyall  Makefile
   pyproject.toml  requirements.lock  src  tests

   $ docker run --rm bookshelf:copyall cat /app/.env
   POSTGRES_PASSWORD=hunter2

108 MB sent to the daemon, 107 MB more in the image (your host's ``.venv``, which the
container never uses), the Git history, the tests, and the **database password**, now
readable by anyone who can pull the image. Deleting the file in a later layer would
not help: the earlier layer still contains it.

A ``.dockerignore`` file excludes paths from the context, whatever the Dockerfile
says. Create it next to the Dockerfile:

.. code-block:: text

   # Version control and editor state
   .git/
   .gitignore
   .vscode/
   .idea/

   # Python build/cache artefacts
   __pycache__/
   *.py[cod]
   *.egg-info/
   .venv/
   .pytest_cache/
   .ruff_cache/
   .coverage
   htmlcov/

   # Local data and secrets — never bake these into an image
   *.db
   .env
   .env.*

   # Not needed at runtime
   tests/
   docker-compose*.yml
   Dockerfile*
   Makefile

The syntax is the same as ``.gitignore``. Rebuild the ``COPY . .`` variant:

.. code-block:: bash

   $ docker build -f Dockerfile.copyall -t bookshelf:copyall .
    => => transferring context: 15.30kB                                    0.0s
   ...
   $ docker images bookshelf:copyall
   REPOSITORY   TAG       IMAGE ID       CREATED          SIZE
   bookshelf    copyall   ca59e6c40f40   2 seconds ago    195MB

   $ docker run --rm bookshelf:copyall ls -a /app
   .  ..  .dockerignore  pyproject.toml  requirements.lock  src

   $ docker run --rm bookshelf:copyall cat /app/.env
   cat: /app/.env: No such file or directory

Treat ``.dockerignore`` as mandatory even when your own Dockerfile copies files
selectively. It is the safety net for the day someone adds ``COPY . .``, and for
older builders that transfer the whole directory.

Inspecting the Image
---------------------

``docker image inspect`` (or the shorter ``docker inspect``, which works on images and
containers alike) prints everything Docker knows about an image as JSON:

.. code-block:: bash

   $ docker image inspect bookshelf:v1
   [
       {
           "Id": "sha256:4a681bc3531778ce29a2019170afe2cd6d76bb55855f26cfea98d179ee54464c",
           "RepoTags": [
               "bookshelf:v1"
           ],
           "Created": "2026-10-28T18:10:33.600860426Z",
           "Config": {
               "User": "",
               "ExposedPorts": {
                   "8000/tcp": {}
               },
               "Env": [
                   "PATH=/usr/local/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin",
                   "LANG=C.UTF-8",
                   "GPG_KEY=7169605F62C751356D054A26A821E680E5FA6305",
                   "PYTHON_VERSION=3.12.16",
                   "PYTHON_SHA256=b5796915dc45ff745cfb4e990a7e7c93d6f546328a102ce31448d69ebc37575c",
                   "PYTHONPATH=/app/src"
               ],
               "Cmd": [
                   "uvicorn",
                   "bookshelf.main:app",
                   "--host",
                   "0.0.0.0",
                   "--port",
                   "8000"
               ],
               "WorkingDir": "/app",
               "Entrypoint": null,
               ...
           },
           "Architecture": "amd64",
           "Os": "linux",
           "Size": 195200031,
           "RootFS": {
               "Type": "layers",
               "Layers": [ ... ]
           },
           ...
       }
   ]

The ``Config`` block is your Dockerfile, as Docker will execute it. ``ENV`` became
``Env``, ``WORKDIR`` became ``WorkingDir``, ``EXPOSE`` became ``ExposedPorts``, and
``CMD`` became ``Cmd``. Note the entries you did *not* write. ``PATH``, ``LANG`` and
``PYTHON_VERSION`` are inherited from ``python:3.12-slim``, so an image's
configuration is the sum of its own instructions and its base image's. An empty
``User`` means the container runs as root.

The full JSON is long. ``--format`` takes a Go template and extracts just the field you
need, which is handy in scripts and when debugging:

.. code-block:: bash

   $ docker image inspect bookshelf:v1 --format '{{json .Config.Cmd}}'
   ["uvicorn","bookshelf.main:app","--host","0.0.0.0","--port","8000"]

   $ docker image inspect bookshelf:v1 --format '{{range .Config.Env}}{{println .}}{{end}}'
   PATH=/usr/local/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
   LANG=C.UTF-8
   GPG_KEY=7169605F62C751356D054A26A821E680E5FA6305
   PYTHON_VERSION=3.12.16
   PYTHON_SHA256=b5796915dc45ff745cfb4e990a7e7c93d6f546328a102ce31448d69ebc37575c
   PYTHONPATH=/app/src

   $ docker image inspect bookshelf:v1 \
       --format '{{len .RootFS.Layers}} layers, {{.Size}} bytes, {{.Os}}/{{.Architecture}}'
   8 layers, 195200031 bytes, linux/amd64

Eight layers: four from the base image, plus one each for ``WORKDIR``, ``COPY
requirements.lock``, ``RUN pip install`` and ``COPY src/``. ``ENV``, ``EXPOSE`` and
``CMD`` change only metadata, so they add no layer.

Use it whenever an image does not behave as expected. "Which command does this image
actually run?", "is it the arm64 or amd64 build?" and "which environment variables are
baked in?" all have a one-line answer here, without starting a container. Anyone who
can pull the image can run the same command. That matters for secrets, as you will see
in :ref:`ch04_multistage`.

Layer Caching
--------------

Docker caches each layer. When rebuilding, it reuses a cached layer if the instruction
*and its inputs* are unchanged. For ``COPY``, the inputs are the file contents. The
first changed layer — and **every layer after it** — is rebuilt.

That is why the Dockerfile copies the lockfile and installs dependencies *before*
copying the source. Change a line of code and rebuild:

.. code-block:: bash

   $ echo "# reviewed" >> src/bookshelf/main.py
   $ time docker build -t bookshelf:v1 .
   [+] Building 0.8s (10/10) FINISHED
    => [internal] load build definition from Dockerfile                    0.0s
    => [internal] load .dockerignore                                       0.0s
    => [internal] load metadata for docker.io/library/python:3.12-slim     0.0s
    => [1/5] FROM docker.io/library/python:3.12-slim                       0.0s
    => [internal] load build context                                       0.0s
    => => transferring context: 1.21kB                                     0.0s
    => CACHED [2/5] WORKDIR /app                                           0.0s
    => CACHED [3/5] COPY requirements.lock .                               0.0s
    => CACHED [4/5] RUN pip install --no-cache-dir -r requirements.lock    0.0s
    => [5/5] COPY src/ ./src/                                              0.3s
    => exporting to image                                                  0.0s

   real    0m0.832s

0.8 seconds instead of 12.6. Now compare a Dockerfile that copies everything first:

.. code-block:: dockerfile

   # Anti-pattern: any source change invalidates the pip install layer
   FROM python:3.12-slim
   WORKDIR /app
   COPY . .
   RUN pip install --no-cache-dir -r requirements.lock
   ...

.. code-block:: bash

   $ echo "# again" >> src/bookshelf/main.py
   $ time docker build -f Dockerfile.badorder -t bookshelf:badorder .
    => CACHED [2/4] WORKDIR /app                                           0.0s
    => [3/4] COPY . .                                                      0.0s
    => [4/4] RUN pip install --no-cache-dir -r requirements.lock          10.1s
    ...
   real    0m10.929s

Every code change re-downloads and reinstalls every dependency. On a laptop that is an
annoyance; in a CI pipeline building dozens of times a day (Chapter 5) it is minutes of
wasted time per build, and a hard dependency on PyPI being reachable.

.. admonition:: Observation:

   The rule generalizes: **order instructions from least to most frequently changed.**
   Base image, then system packages, then dependency manifest and install, then source
   code. Anything that changes on every commit goes last.

**Exercises**

#. Generate ``requirements.lock`` (if you have not already), then write the
   ``Dockerfile`` and ``.dockerignore`` shown above. Build the image:

   .. code-block:: bash

      $ docker build -t bookshelf:v1 .

   Run it with ``docker run -d --name bookshelf -p 8000:8000 bookshelf:v1`` and open
   http://localhost:8000/docs in a browser. Create a book through the Swagger UI, then
   fetch it with ``curl http://localhost:8000/books/1``.

#. Inspect your image with ``docker image inspect bookshelf:v1``. Using ``--format``,
   print only its ``Cmd``, its ``WorkingDir``, and its architecture. Then run
   ``docker image inspect python:3.12-slim --format '{{json .Config.Cmd}}'``. Which of
   your image's settings came from your Dockerfile and which were inherited?

#. Change the ``CMD`` to bind to ``127.0.0.1`` instead of ``0.0.0.0``. Rebuild, rerun,
   and ``curl`` the health endpoint. What error do you get? Use
   ``docker exec bookshelf python -c "import urllib.request; print(urllib.request.urlopen('http://127.0.0.1:8000/health').read())"``
   to show that the server *is* working inside the container. Revert the change.

#. Measure layer caching. Add a comment to ``src/bookshelf/main.py`` and time the
   rebuild. Which steps say ``CACHED``? Then add a comment to ``requirements.lock`` and
   rebuild again. Which steps are re-executed now, and why?

#. Write ``Dockerfile.badorder`` with ``COPY . .`` before ``pip install``. Build it once,
   change a source file, and time the rebuild. Compare with the previous exercise.

#. Remove the ``.dockerignore`` temporarily, create a file ``.env`` containing
   ``SECRET=hunter2``, and build ``Dockerfile.badorder``. Then run
   ``docker run --rm bookshelf:badorder cat /app/.env``. Restore ``.dockerignore``,
   delete ``.env``, and remove the image with ``docker rmi bookshelf:badorder``.

#. Delete the container with ``docker rm -f bookshelf`` and start a new one from the same
   image. Is the book you created still there? Where was it stored?
