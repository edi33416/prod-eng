.. _ch04_dockerfile:

Writing Dockerfiles
====================

.. note::

   Work in your BookShelf project (or a copy of ``support/bookshelf-ch4/``). All commands
   on this page run from the project root — the directory containing ``pyproject.toml``.

-----

From Lockfile to Image
-----------------------

A ``Dockerfile`` is a recipe: a sequence of instructions, each of which produces one
image layer. Docker executes it top to bottom with ``docker build``.

The image needs the exact dependency versions you test with. You already have the tool
for that from :ref:`ch01_deps` — generate a runtime lockfile (no dev extras) if your
project does not have one yet:

.. code-block:: bash

   $ pip-compile --strip-extras --output-file=requirements.lock pyproject.toml
   $ head -12 requirements.lock
   #
   # This file is autogenerated by pip-compile with Python 3.12
   # by the following command:
   #
   #    pip-compile --output-file=requirements.lock --strip-extras pyproject.toml
   #
   annotated-doc==0.0.5
       # via fastapi
   annotated-types==0.8.0
       # via pydantic
   anyio==4.15.1
       # via

The image installs from ``requirements.lock``, not from ``pyproject.toml``. ``pyproject``
says what the project *accepts* (``fastapi>=0.111``); the lockfile says what was *tested*
(``fastapi==0.162.0``). Production gets the tested set.

-----

Dockerfile Instructions
------------------------

.. list-table::
   :header-rows: 1
   :widths: 18 82

   * - Instruction
     - What it does
   * - ``FROM``
     - Base image to build on. Every Dockerfile starts with one.
   * - ``WORKDIR``
     - Set (and create) the working directory for later instructions and for the
       container at runtime.
   * - ``COPY``
     - Copy files from the **build context** (the directory you pass to
       ``docker build``) into the image.
   * - ``RUN``
     - Execute a command at *build* time and save the resulting filesystem as a layer.
   * - ``ENV``
     - Set an environment variable, both for later build steps and at runtime.
   * - ``EXPOSE``
     - Document which port the application listens on. It does *not* publish the
       port — ``docker run -p`` does that.
   * - ``CMD``
     - Default command when the container starts. Overridable on ``docker run``.
   * - ``ENTRYPOINT``
     - Fixed executable for the container; ``CMD`` then supplies default *arguments*
       to it. Useful for CLI-tool images; for a web service, ``CMD`` alone is enough.
   * - ``USER``
     - User (and group) that later ``RUN`` steps and the container process run as.

-----

A First Dockerfile for BookShelf
---------------------------------

Create ``Dockerfile`` in the project root:

.. code-block:: dockerfile

   FROM python:3.12-slim

   WORKDIR /app

   COPY requirements.lock .
   RUN pip install --no-cache-dir -r requirements.lock

   COPY src/ ./src/
   ENV PYTHONPATH=/app/src

   EXPOSE 8000
   CMD ["uvicorn", "bookshelf.main:app", "--host", "0.0.0.0", "--port", "8000"]

Line by line:

- ``python:3.12-slim`` — Debian with Python 3.12 and nothing else. The ``slim`` variant
  drops compilers and headers; you will see why that matters in :ref:`ch04_multistage`.
- ``--no-cache-dir`` — pip's download cache is useless inside an image and would add
  tens of megabytes to the layer.
- ``PYTHONPATH=/app/src`` — makes the ``bookshelf`` package importable from the
  ``src/`` layout without ``pip install``-ing the project itself.
- ``--host 0.0.0.0`` — inside a container, ``127.0.0.1`` is the *container's* loopback
  interface. A server bound to it is unreachable from the host, even with ``-p``. Bind
  to all interfaces.
- ``CMD [...]`` in **exec form** (a JSON array) — uvicorn runs directly as PID 1 and
  receives ``SIGTERM`` on ``docker stop``. The *shell form* (``CMD uvicorn ...``) wraps
  it in ``/bin/sh -c``, and the shell does not forward signals to its child.

.. warning::

   ``--host 127.0.0.1`` (uvicorn's default) is the single most common reason for "the
   container is running but ``curl`` fails". The symptom is
   ``curl: (52) Empty reply from server`` or ``Connection reset by peer``: Docker's
   port proxy accepts the connection, but nothing in the container is listening on the
   interface it forwards to. If you see that, check the bind address first.

The .dockerignore File
-----------------------

``docker build .`` sends the whole directory — the **build context** — to the Docker
daemon before the first instruction runs. Without a filter, that includes ``.git/``,
``.venv/`` (hundreds of MB), your local ``bookshelf.db``, and ``.env`` with real secrets.

Create ``.dockerignore`` next to the Dockerfile:

.. code-block:: text

   # Version control and editor state
   .git/
   .gitignore
   .vscode/
   .idea/

   # Python build/cache artefacts
   __pycache__/
   *.py[cod]
   *.egg-info/
   .venv/
   .pytest_cache/
   .ruff_cache/
   .coverage
   htmlcov/

   # Local data and secrets — never bake these into an image
   *.db
   .env
   .env.*

   # Not needed at runtime
   tests/
   docker-compose*.yml
   Dockerfile*
   Makefile

The syntax is the same as ``.gitignore``. With it, the build context for BookShelf is
about 12 kB. Without it, a ``COPY . .`` would happily copy ``.env`` into a layer — and
anyone who can pull the image can extract it, even if a later layer deletes the file.

Two things should bother you. The API runs as **root**. And the SQLite database lives
**in the container's writable layer, next to the source code** — ``docker rm`` deletes
every book. Both are fixed later in this chapter.

-----

Layer Caching
--------------

Docker caches each layer. When rebuilding, it reuses a cached layer if the instruction
*and its inputs* are unchanged. For ``COPY``, the inputs are the file contents. The
first changed layer — and **every layer after it** — is rebuilt.

That is why the Dockerfile copies the lockfile and installs dependencies *before*
copying the source. Change a line of code and rebuild:

.. code-block:: bash

   $ echo "# reviewed" >> src/bookshelf/main.py
   $ time docker build -t bookshelf:v1 .
   [+] Building 0.8s (10/10) FINISHED
    => [internal] load build definition from Dockerfile                    0.0s
    => [internal] load .dockerignore                                       0.0s
    => [internal] load metadata for docker.io/library/python:3.12-slim     0.0s
    => [1/5] FROM docker.io/library/python:3.12-slim                       0.0s
    => [internal] load build context                                       0.0s
    => => transferring context: 1.21kB                                     0.0s
    => CACHED [2/5] WORKDIR /app                                           0.0s
    => CACHED [3/5] COPY requirements.lock .                               0.0s
    => CACHED [4/5] RUN pip install --no-cache-dir -r requirements.lock    0.0s
    => [5/5] COPY src/ ./src/                                              0.3s
    => exporting to image                                                  0.0s

   real    0m0.832s

0.8 seconds instead of 12.6. Now compare a Dockerfile that copies everything first:

.. code-block:: dockerfile

   # Anti-pattern: any source change invalidates the pip install layer
   FROM python:3.12-slim
   WORKDIR /app
   COPY . .
   RUN pip install --no-cache-dir -r requirements.lock
   ...

.. code-block:: bash

   $ echo "# again" >> src/bookshelf/main.py
   $ time docker build -f Dockerfile.badorder -t bookshelf:badorder .
    => CACHED [2/4] WORKDIR /app                                           0.0s
    => [3/4] COPY . .                                                      0.0s
    => [4/4] RUN pip install --no-cache-dir -r requirements.lock          10.1s
    ...
   real    0m10.929s

Every code change re-downloads and reinstalls every dependency. On a laptop that is an
annoyance; in a CI pipeline building dozens of times a day (Chapter 5) it is minutes of
wasted time per build, and a hard dependency on PyPI being reachable.

.. admonition:: Observation:

   The rule generalizes: **order instructions from least to most frequently changed.**
   Base image, then system packages, then dependency manifest and install, then source
   code. Anything that changes on every commit goes last.

**Exercises**

#. Generate ``requirements.lock`` (if you have not already), then write the
   ``Dockerfile`` and ``.dockerignore`` shown above. Build the image:

   .. code-block:: bash

      $ docker build -t bookshelf:v1 .

   Run it with ``docker run -d --name bookshelf -p 8000:8000 bookshelf:v1`` and open
   http://localhost:8000/docs in a browser. Create a book through the Swagger UI, then
   fetch it with ``curl http://localhost:8000/books/1``.

#. Change the ``CMD`` to bind to ``127.0.0.1`` instead of ``0.0.0.0``. Rebuild, rerun,
   and ``curl`` the health endpoint. What error do you get? Use
   ``docker exec bookshelf python -c "import urllib.request; print(urllib.request.urlopen('http://127.0.0.1:8000/health').read())"``
   to show that the server *is* working inside the container. Revert the change.

#. Measure layer caching. Add a comment to ``src/bookshelf/main.py`` and time the
   rebuild. Which steps say ``CACHED``? Then add a comment to ``requirements.lock`` and
   rebuild again. Which steps are re-executed now, and why?

#. Write ``Dockerfile.badorder`` with ``COPY . .`` before ``pip install``. Build it once,
   change a source file, and time the rebuild. Compare with the previous exercise.

#. Remove the ``.dockerignore`` temporarily, create a file ``.env`` containing
   ``SECRET=hunter2``, and build ``Dockerfile.badorder``. Then run
   ``docker run --rm bookshelf:badorder cat /app/.env``. Restore ``.dockerignore``,
   delete ``.env``, and remove the image with ``docker rmi bookshelf:badorder``.

#. Delete the container with ``docker rm -f bookshelf`` and start a new one from the same
   image. Is the book you created still there? Where was it stored?
